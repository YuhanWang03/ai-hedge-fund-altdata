# `v2/agent` — 模型驱动的 Agent 循环（与现有单跳路由对比）

新增包，**不修改 `v2/bot` 任何一行**。把同一套 24 个 responder 重新暴露成模型可调用
的工具，让模型自己决定调什么、调几次、按什么顺序，和生产现有的单跳意图路由做
**可测量**的对比。下面这一页是五分钟版本；每个数字在后面都有它的那一轮。

---

## 一页纸

### 做了什么

- **一个工具调用循环**（`loop.py`）：预算、去重、错误即观测、近因加权压缩、强制收尾。
  五个机制各对应一种在实盘里真发生过的故障。
- **一个路由层**（`router.py`）：按问题判断「多步规划值不值 10 倍的钱」，单跳能答的
  留给单跳，`/ask` 可强制升级。写操作永远不升级。
- **两个机械校验**：数字溯源（答案里每个数都要能在本轮某个工具返回里找到，或写出
  算式）和归属检查（数字对、主体错）。都不用第二个模型，都会触发一次重写。
- **一套评测**（`eval/`）：89 条标注问题、10 类、4 档配置、重复采样，外加校验器
  自己的两条错误率轴，和一份 15 条从 Telegram 实测取的留出集。
- **15 轮迭代**，每轮先量再改，失败的实验和自己标错的答案键都留在记录里。

### 量了什么

| | 单跳基线 | routed | **production（线上）** | 完整循环 |
|---|---|---|---|---|
| 开发集通过率（89 × 3） | 53% | 96% | **92–95%** | 97% |
| 每通过 token | — | 5,455 | **4,404** | 9,396 |
| **留出集通过率**（15 × 3，从未用来调过） | 47% | 84% | **82%** | **100%** |
| 路由准确率 开发集 / 留出集 | — | 98% / **87%** | 同左 | — |
| 归属误报 · 重写丢事实（/267） | — | 0 · 0 | 1 · 0 | 0 · 0 |

三个数字值得记住：路由用 57% 的成本拿到了完整循环 99% 的通过率；线上那档再便宜
四分之一，代价 1–3pp；**在没见过的问题上，完整循环没掉分，掉分的是手写路由**。
两次全量之间 production 差 3pp，这套评测的分辨率约 ±2pp，小于这个的差别读不出来。

### 学到了什么

1. **校验器不奖励的规则，模型不会遵守。** 让检查真的接受某种写法，模型立刻照做；只改 prompt 零效果。（第 5 轮）
2. **单次评测的失败清单大部分是噪声。** 同配置两轮，25 条失败只重合 9 条；不重复采样就会去修从来没坏过的东西。（第 3 轮）
3. **指标会骗人。** 「18% 溯源失败」拆开看 71% 是检查自己的假阳性。（第 4 轮）
4. **描述能改「选哪个工具」，改不了「要不要再调一个」。** 补一个模型发现不了的事实有效；补程序、补价目表零响应，多出来的 token 全是标签本身。（第 10–11 轮）
5. **校验器的错误率要在它拒掉的那份文本上量。** 警告打在正确初稿上、重写把事实一起扔掉，会被记成模型的失败，而校验器的误报率读 0。（第 14 轮）
6. **过拟合的是手写规则，不是模型。** 留出集上完整循环 100%，规则路由 87%。（第 15 轮）

### 接下来看哪

- 想看数字怎么来的：下一节完整结果表，再往下是十五轮的逐轮记录。
- 想看机制：§1 控制流归谁、§2 五个机制、§7 路由什么时候值得。
- 想看评测怎么建的：§12，包括答案键自己被测的那几条。
- 想看没做到的：「已知限制」和 §13。

## 完整结果

89 条标注 query，每条跑 3 次（267 次运行），工具层为录制观测，只有模型是变量。
四档：**baseline** 是生产现有的单跳路由；**routed** 让路由层按问题挑路，上限 20 次
调用；**production** 是线上真正跑的配置，上限 8 次；**agent** 是不经路由的完整循环。

| | baseline（现状） | routed（20 次） | **production（8 次，线上）** | agent（20 次） |
|---|---|---|---|---|
| **通过率** | 53% | 96% | **92%**（上一次全量 95%） | 97% |
| 工具召回 | 70% | 98% | 98% | 99% |
| 事实召回 | 63% | 98% | 97% | 99% |
| 溯源率 | 100% | 99% | 97% | 99% |
| **归属误报** | — | 0 / 267 | 1 / 267（已修） | 0 / 267 |
| **重写丢事实** | — | 0 / 267 | 0 / 267 | 0 / 267 |
| 路由准确率 | — | 98% | 98% | — |
| 超预算率 | 0% | 11% | **6%** | 16% |
| token / 例 | 0 | 5,210 | **4,057** | 9,080 |
| **每通过 token** | — | 5,455 | **4,404** | 9,396 |
| 稳定失败 | — | 2 条 | 4 条 | 1 条（r07） |

同一份代码的两次全量（中间只改了重写指令）production 差 3pp、routed 持平、agent +1pp：
**89 × 3 这套评测的分辨率大约是 ±2pp**，小于这个的差别读不出来。上一次是
95% / 4,137，两次都在表里，取哪个都不比取另一个更诚实。

分类别（baseline / routed / **production** / agent）：

```
single_lookup  100 / 100 / 100 / 100      multi_hop   29 /  93 /  93 / 100
cost_trap      100 / 100 / 100 /  94      ranking     30 /  87 /  73 /  83
honesty         86 / 100 / 100 / 100      compound     0 /  96 /  92 /  96
causal          75 / 100 /  88 /  96      recovery     0 /  73 /  80 / 100
dead_end         0 / 100 /  90 / 100      checker_stress 67 / 100 / 100 /  94
```

**结论：路由是对的，线上那个更紧的配置也是对的。** 单跳在它设计要解决的问题上是
满分，在需要跨工具组合的地方（multi_hop 29%、compound 0%、recovery 0%）几乎为零；
路由拿走了完整循环几乎全部的上行（差 1pp），成本只有 57%。**production 再把调用
上限从 20 收到 8，又便宜 19%，代价 1–3pp**，掉的集中在 `ranking` 和 `causal`。

这条结论回答了一个很自然的产品提议：「把所有自然语言提问都交给 agent，斜杠命令
才给卡片」。**不要做** —— 那等于花 1.7 倍的钱换 1pp，而且完整循环恰恰在最简单的
一类（cost_trap 94%）上不如路由，最简单的查询会变成最不可靠的。

留出集的 15 条和它的结果单独一节，在十五轮记录之后。

## 十五轮迭代：改的是什么

最终分数不如这条线值钱 —— 六轮里**有三轮我修的是自己的评测，不是模型**。

| 轮次 | 发现 | 处置 | agent |

六条可迁移的结论：

1. **校验器不奖励的规则，模型不会遵守。** 第 5 轮只改 prompt 毫无效果，让检查真的
   接受该行为后，模型立刻照做。
2. **单次评测的失败清单大部分是噪声。** 没有重复采样，第 3 轮我会去修 21 条从来
   没坏过的东西。
3. **指标本身会骗人。** 「18% 溯源失败」听起来像模型在编，拆开看 71% 是检查的
   假阳性 —— 做评测的人必须能解释自己的指标在拒绝什么。
4. **描述能改变「选哪个工具」，改变不了「要不要再调一个」。** 两轮实验各出一半：
   第 10 轮补一个模型发现不了的事实（这张卡没有行业列），一条稳定失败当场消失；
   第 11 轮补上八十倍价差的价目表，行为零响应 —— 增加的 1,048 token 全部是标签
   自己的开销（预测 1,089，实测 1,048）。分类问题描述能管，**停止问题只能靠机制**，
   因为循环里根本没有「够了」这个信号。
5. **校验器的错误率要在它拒掉的那份文本上量，不能只量最终答案。** 误报轴只看
   「最终答案正确却被警告」，而一个打在正确初稿上的警告会触发重写，重写把被点名的
   数字连同其余事实一起删掉，最后按「事实缺失」记在模型头上——校验器自己的分数
   一直是 0/60。m07 有 8/10 的失败是这个形状（第 14 轮）。
6. **过拟合的是手写规则，不是模型。** 留出集上完整循环 100%，规则路由 87%——它的
   98% 是对着 89 条调出来的。两条漏判的形状一样：双主题问题里有一个主题不在词表
   （木头姐、NFP）。词表加词是最容易过拟合的动作，加了就得再造一份留出集来验。

## 评测的第四条轴：归属检查的误报率

前九轮实盘暴露了七个归属误报——正确的回答被打上「张冠李戴」的标记。**没有
一个是评测集发现的**：用例通过了，那条 ⚠️ 没人计分，最后是人读 Telegram
读出来的。

评测有 grounding 轴，却没有 attribution 轴。现在有了：

- 一条用例的事实、工具与禁词断言全部通过，就意味着它**已经**把对的数字配给了
  对的公司。此时归属检查仍然报警，那按定义就是误报——检查器拒掉了正确答案。
- `CaseScore.false_misattribution` 记录它，`false_misattribution_rate` 汇总它，
  并且**让用例失败**。不失败的指标没人会去看。
- 回答本身就是错的时候（事实缺失、命中禁词），警告不算在检查器头上。

配套的 `checker_stress` 六条用例不测模型，测的是**打垮过检查器的形状**：日期
列（每个日子都会被读成负数）、阈值（不归任何主体所有）、窗口长度（52 周 /
200 日）、模型当场算出的百分比、行业标签。fixture 也按真实卡片的排版改回了
刁钻的样子——日期在前、标的在后，这正是当初错位一行的原因。

措辞没法固定，这恰恰是重点：形状会重复出现，用词不会。一份记着七个已修 bug
原句的清单，只能重新发现那七个。

### 三轮测量，以及它证伪的一个判断

| 轮次 | routed | agent | 备注 |
|---|---|---|---|
| 单轮 | 0 / 89 | 2 / 89（2.2%） | 样本太小，形状不可靠 |
| repeat=3 | 5 / 267 | **12 / 267（4.5%）** | 与单轮几乎不重合 |
| repeat=3（修复后） | **0 / 267** | **2 / 267（0.75%）** | |

第一次测到 2.2% 时，我据此撤回了一个更贵的重构提议。**那个判断的依据不够** ——
重复采样把真实值抬到 4.5%，而且报的形状和单轮几乎完全不同。这是「单次评测的
失败清单大部分是噪声」这条规律在新轴上的复现，我在自己刚写下它的地方又踩了
一次。

### 修的是分析单元，不是又一条补丁

带上原句之后，14 条误报里的形状是同一个：

```
前三大持仓 CRWD + NVDA + MSFT 合计 22.4% + 18.2% + 14.1% = 54.7%
前 3 大合计 22.4%（CRWD）+ 18.2%（NVDA）+ 14.1%（MSFT）= 54.7%
NVDA 在超预期幅度（+5.6% vs +2.9%）…上都领先 AMD
```

这些句子把数字和主体**成组配对**，而「离得最近的那个名字」把每一对都读错一位。
检查器的分析单元从一开始就选错了。此前所有修复 —— 换行截断、项目符号截断、
中文定语后置、基准句式 —— 都是在这个错误前提上打补丁。

现在的原则一句话说得完：

> **邻近只在一个从句只提到一个主体时才携带信息。** 多个主体共享一个从句时，
> 配对是结构性的，检查器无法解析 —— 于是弃权，除非**没有任何一个**主体拥有
> 这个数字。

那个「除非」是它仍然抓得住 h04（把 ARKK 的数据安到 ARKQ 头上）和 h07（给每只
持仓都套上 NVDA 的机构比例）的原因。单元是**从句**不是整行：
「NVDA Vanguard 8.94%；AMD Vanguard 8.94%」共用一行，而这个检查存在的理由整个
住在第二句里 —— 第一版用整行，h07 的测试立刻红了。

配套四条，各由一句实盘原句逼出来：比较句的第二个操作数属于被比较的那一方
（`$1.31 vs $0.71` 里的 0.71 是 AMD 的）、当界线用的数字不归任何人（`20 以下`）、
观测侧窗口同样在行尾收束、否认归属的句子不算归属（`那些数字都不是 ARKQ 的`）。

**观测侧那条值得单独记。** 我当初特意没做，注释里的理由是「观测侧多记几个归属者
只会减少误报，宽松是保守方向」。这个推理是错的：一行末尾的 ticker 会继续拥有
下一行的组合级数字，于是「组合当前回撤 -4.20%」成了 MSFT 的。**无边界的宽松
不是多给归属者，是多给错的归属者。**

### 诊断信息本身也是一次修复

`MSFT←18.2(实为 NVDA)` 说清了结论，一个字没说为什么。我照 fixture 拼了五种
合理的答案排版去复现，五种全是绿的 —— 线索到此为止。现在每条 finding 带上
触发它的答案原句，报告和 JSON 里都有。**不指名数字的「数字无法溯源」是不可
行动的判词，不给出句子的归属误报也是。**

## 一次对照实验：工具描述能修好什么，修不好什么

评测清干净之后，只剩两条稳定失败，都是**工具选择**而非表达：模型放着权威卡片
不用，或者查得停不下来。这是一个可以做对照的机会 —— 因为这个项目最贵的一条
经验正好指向反面：

> 第 5 轮：三轮 prompt 硬化要求模型「写出算式」，加总失败率纹丝不动 30%；
> 改成让检查器接受写出的算式，模型立刻照做。**校验器不奖励的规则，模型不会遵守。**

那么工具描述是不是也一样没用？改动前记下基线，改三条描述，只跑一轮，对着看。

### 改了什么

| 工具 | 补的内容 | 类型 |
|---|---|---|
| `portfolio_view` | 「没有行业列；板块归属不在这张卡里，risk_view 是唯一来源」 | 一个**事实** |
| `risk_view` | 「板块占比的唯一来源，没有别的工具记录板块归属」 | 一个**事实** |
| `watchlist_view` | 「只有代码，没有行情；成员近况要逐个查」 | 一条**程序** |

### 结果：一半有效，一半无效

| 指标 | 改前 | 改后 | 判读 |
|---|---|---|---|
| **k06**（漏调 `risk_view`） | **0 / 3** | **3 / 3** | ✅ 有效 |
| **m07** 工具调用次数 | 14–20 | 19–20（通过率 2/3 → 1/3） | ❌ 无效，还更差 |
| **r07** 工具调用次数 | 16–20 | 10–20 | ❌ 噪声内 |
| 工具召回（routed / agent） | 99% / 98% | 98% / 99% | 各差 1pp，噪声 |
| 超预算率 | 14% / 24% | **10% / 20%** | 各降 4pp |
| 工具 / 例 | 3.7 / 4.5 | 3.4 / 4.2 | 降 0.3 |
| 每通过 token | 5,867 / 10,903 | **5,629 / 10,298** | 降 5% |

（同一轮里 `c08` 也从 0/3 恢复，但那是**上一步修标注**的功劳，不算在这次实验
头上 —— 它的问句原本写「上周…这周」，而 `pnl_period` 的枚举里根本没有上周。）

### 失败的那一半更值钱

两条描述改动，一条成功一条失败，而它们的差别把那条老教训切得更细了：

- **补事实有效。** 「这张卡没有行业列」是模型**无法自己发现**的信息 —— 它调完
  `portfolio_view` 才知道，可那时它已经拿到权重了，凑一凑就出来
  （`18.2 + 11.3 + 8.6 = 38.1`，数字全对），没有理由再去调 `risk_view`。
  工具选择本来就靠描述做，补上这条事实，k06 从 0/3 变 3/3。

- **补程序无效。** 「成员近况要逐个查」写了等于没写，因为 **m07 的病根不是
  「不知道下一步做什么」，是「不知道什么时候停」** —— 它跑了 19–20 次工具调用，
  一直在查成员。描述能告诉它从哪开始，管不了它在哪结束。

所以更准确的说法不是「补事实 vs 提要求」，而是：

> **描述能纠正「选错了工具」，纠正不了「不知道收敛」。** 后者是预算和循环
> 终止条件的范畴，写在 prompt 里的任何一句话都碰不到它。

超预算率降的那 4pp 也符合这个解释：它来自 `portfolio_view` / `risk_view` 那两条
（模型少走了一趟弯路），而不是来自 `watchlist_view`。

这三条事实现在有测试钉着（`test_the_collection_tools_say_what_they_lack_and_what
_comes_next`），注释里写明它们来自测量而不是品味 —— 将来有人「整理」描述时会
被拦一下。

## 第 11 轮：一个被证伪的假设，以及它把上一条结论切得更细

第 10 轮的结论是「补事实有效，补程序无效」。第 11 轮拿它做了一次外推，**失败了**。

### 假设

`registry` 里一直有 `cost_hint` —— 0.1 秒（watchlist）到 8 秒（summary），
**八十倍的价差** —— 注释写着「used only for budgeting/telemetry display」，而
循环里哪儿都没显示。模型是在一个**平价成本模型**下做规划的。

线上差距比秒数还大：`explain_move` 内部是一次 Tavily 搜索加两次模型调用，完全
不出现在循环自己的 token 统计里；对八只持仓扇出一次就是八次搜索、十六次模型
调用，而模型的上下文里这和八次廉价查表长得一模一样。

这看起来正是第 10 轮那种「模型无法自己发现的事实」。于是把价格写进每个工具的
描述，**刻意写成价格而不是命令** —— 没有一句话叫它省着用。

### 结果：行为一点没变，只有账单变贵

| 指标 | 改前 | 改后 |
|---|---|---|
| 工具 / 例（agent） | 4.2 | 4.1 |
| 通过率（routed / agent） | 94% / 93% | 94% / 94% |
| **token / 例（agent）** | 9,604 | **10,652（+1,048）** |
| **每通过 token（routed）** | 5,629 | **6,253（+11%）** |
| 超预算率 | 10% / 20% | 13% / 21% |

关键是最后一步核算：24 个工具的价格标签本身是 **218 token 的 schema，每次 LLM
调用都要重传一遍**；agent 每例约 5 次调用 → **预测 +1,089**，实测 **+1,048**。

**标签的开销完整解释了全部增量。** 也就是说模型对价格的响应是零 —— 它没有少调
一次贵工具，只是每次都多读了一遍价目表。

### 修正后的结论

不是「事实 vs 程序」，而是：

> **描述能改变「在几个工具里选哪个」，改变不了「要不要再调一个」。**

第 10 轮成功的那两条改的是**分类问题**（板块占比该查哪张卡）；失败的那条
（watchlist「成员要逐个查」）和这一轮的价格，改的都是**停止问题**。而停止问题
在这个循环里**根本没有反馈信号** —— 工具返回之后，没有任何东西告诉模型「够了」。
往 prompt 里塞再多信息也碰不到它。

这条和 m07 的诊断收敛到同一点，两次独立的实验指向同一个机制缺口。

代码已回滚，并用一条测试**钉住这个删除**（`test_the_schema_does_not_carry_prices`）
—— 这是那种「听上去显然对、一数就显然错」的改动，注释里写明重加之前请重新测量，
不要重新推理。`cost_hint` 本身留着，它是真的。

### 那停止问题该怎么修

不能靠描述，只能靠机制。三个候选，都还没测：

1. **收紧硬上限** —— `AgentConfig.max_tool_calls` 现在是 20，而评测标注认为多数
   问题 8–12 次就够。注意：循环并没有「超预算」，它规规矩矩用满了额度，是额度
   本身太宽。
2. **对同一工具的重复扇出设上限** —— r07 一次调了 25 次工具，绝大多数是同一个
   工具换标的。上限会逼它做选择而不是枚举。
3. **让停止有反馈** —— 每步问一次「够了吗」。每步多一次 LLM 调用，很贵，而且
   按上面的教训，「问」本身可能又是一条没有奖励的规则。

前两条是代码层面的强制，不依赖模型配合 —— 按这个项目的经验，这类改动才是有效
的那类。

## 第 12–13 轮：方向 A 收尾 —— 评测测的从来不是线上跑的那个配置

第 11 轮之后剩两个候选：收紧总额、给单个工具设上限。做第二个的时候发现了比
两个候选都重要的事。

### 单工具上限：护栏，不是节流

上限取 8（持仓数），每次合法的逐仓扫描都放行。加上限的同时加了一份**每工具调用
次数的直方图**，因为本地没有 API key，我量不出浪费是「一个工具扇出 25 次」还是
「八个工具各调三次」——两者修法不同，只有前者能被这个上限碰到。

直方图第一次跑就自己戳破了一个计数 bug：`explain_move×12 · 被上限拦下 4 次`，
上限是 8 哪来的 12？**计数把被拒绝的调用也算成了调用** —— 上限每拦一次，「工具
调用次数」就 +1，这个机制在抬高它被装上来压低的那个数字。修正后：`tool_calls`
只数真正到达工具的，被拒的单独记。这让超预算率跨版本不可比，基线重记。

修正后的形状：

```
m03  8K×8 · insider×8 · portfolio×1          ← 对 8 只持仓各扫两个工具
d05  12 个工具各 1–3 次                        ← 把工具箱扫了一遍
m07  earnings×3 · 8K×3 · explain×3 · flow×3   ← 3 个成员 × 5 个工具
```

上限恰好绑在「合法的全仓扫描」上：它拦住越过 8 的，但**剩下的支出结构上都是
周全** —— `我的持仓最近有什么 SEC 申报` 查了 8-K 又查 Form 4，两者都是 SEC 申报，
不算错。砍掉它等于接受不那么周全的答案，那是产品决定，不是 bug。

### 更基本的：评测一直在测一个生产从不运行的配置

回头看超预算那一段才发现：评测每一轮跑的都是 `AgentConfig()` 默认值，**20 次
调用**；bot 线上是 `production_config()`，**8 次**。追了三轮的「超预算 17–21%」
是生产**从不表现出来**的行为，而真正要紧的问题 —— 8 次上限让通过率掉多少 ——
从来没人量过。

加了一档 `production`（路由 + 5 步 / 8 次 / 90 秒，数字和 `bot_bridge` 锁在一起）。
第一次跑它时它没跑：`run_eval.py` 自己存了一份默认模式列表，runner 的改了它没改，
整轮十分钟什么都没回答。现在只有一份，ast 测试钉住。

### 答案

| | routed（20 次） | production（8 次） | 差 |
|---|---|---|---|
| 通过率 | 95% | 93% | **−2pp** |
| 每通过 token | 5,517 | 4,226 | **−23%** |
| `ranking` | 87% | 73% | −14pp |
| 其余九类 | | | 各 ≤1 条 |

**8 次上限值得。** 它只伤一类问题：排序类（「我持仓里哪只最危险」）需要 risk_view
加逐仓的财报/内部人，8 次确实紧。要把 `ranking` 拿回来，把 `V2_AGENT_MAX_TOOL_CALLS`
提到 10–12，估计多花 10–15% —— **现在这个决定有价签了**，之前没有。

候选 1「收紧总额」不必再做实验：生产早就收紧了，缺的只是量它。方向 A 到此收尾。

## 第 14 轮：方向 B —— 抖动不是一个问题，是三个

方向 A 收尾时剩 6 条抖动（c01 d06 k03 m07 r09 t04），采样温度已经是 0，所以
「调低温度」这个旋钮不存在，「再跑一次」只是重新掷骰子。能做的是把抖动
**按分叉点分类**：每次运行记下它走过的工具路径（`trace`）和答案原文
（`answer`），重复采样后把失败运行和通过运行并排，看第一处不同在哪。

### 第一次 6 × 10

| 用例 | 通过 | 分叉 | 实际是什么 |
|---|---|---|---|
| c01 k03 t04 | 10/10 | — | **3 次采样的噪声**。挂一次就被记成抖动 |
| r09 | 8/10 | 第 1 步选了 `moneyflow_view` | 描述问题：两个描述都说 relative / divergence，谁都没说「对 SPY 的相对强度」在哪张卡 |
| m07 | 9/10 | 路径是通过路径的前缀，自己收尾 | 见下 |
| d06 | 7/10 | 无工具，路径全同，措辞 | 三次失败三个原因 |

三条各修各的：

- **r09** 给 `explain_move` 补一句「这是逆势 / 对 SPY 的 pp」，`moneyflow_view`
  补一句「不是那个，逆势在 explain_move」。第 10 轮的规律再次成立：补一个事实
  改变「选哪个」。单独重跑 8/10 → 9/10，三条一起重跑 **10/10**。
- **d06** 的三次失败：`400` 是初稿里「给 TSLA 设一个 400 美元的提醒」这种示例
  数字，重写时模型道歉「400 是我随口编的，我收回」，把 400 又念了一遍，再挂一次；
  `13` 来自「机构13F持仓」，`\b` 在中文和 F 之间不成立，13F 没被遮掉；`68` 是模型
  把持仓数据直接写进了能力说明，这个是模型的问题，不动。前两个修在校验侧：
  非量遮罩改用字母数字前后断言；重写开头那段「上一条回复…我收回」在校验前剥掉，
  因为**用户从没看过初稿**，这段对他们没有意义。重跑 **10/10**。
- **m07** 的失败答案是这样开头的：「抱歉，我之前的回答把数据张冠李戴了……
  explain_move 的返回里没有标注对应的 ticker，不能采用」。也就是初稿被校验打回，
  重写时模型把整张卡都弃用了。而 JSON 里只有最终答案——初稿和打回原因都没留下。

### 一个看不见的错误率

补上仪器：循环保留被打回的初稿和打回原因，评分新增 `repair_regressed` ——
**初稿事实齐全、经过重写、最终失败**。这是校验器的另一种错误率：误报轴只看
「最终答案正确却被警告」，对初稿的警告它看不见，因为重写把证据一起删了。

带仪器重跑，m07 从 9/10 掉到 **2/10，8 次失败全是这个形状**，而且打回原因是
**空的**：既没有无法溯源的数字，也没有张冠李戴——仪器漏记了第三种发现。补上
之后用真实 registry 复现：

```
summary(ARM)       → 「fixture 模式未记录该 ticker 的综合概览」   (ok, 无数字)
explain_move(ARM)  → 「ARM 为什么动 · 今日 +7.42% …」
初稿：「ARM — 最强，+7.42%（explain_move）」
校验：ARM 的工具返回里没有任何数据，你却给它写了 7.42     ← 错
```

「无数据主体」规则的实现是 `empty - set(owners)`，而 `owners` 是**按数字键**
的字典，减掉的是一堆数字字符串，主体名一个都没减掉。于是一张空卡就足以把
ARM 判成「无数据」，它自己那张 explain_move 卡上的 +7.42% 反倒成了证据。
修法一行：减去持有任何数字的主体集合。h04 那种真正的空主体（ARKQ 只有一张
空卡、答案却写了 ARKK 的权重）仍然会被抓到，测试两头都钉了。

至于为什么第一次 6×10 它是 9/10、带仪器变成 2/10：两次的通过路径不同（前者多调
了 `earnings_view×3`），初稿的句子切分不同，规则命中与否跟着变——这正是
「抖动」的来源，一个确定性 bug 被句子边界调制成了随机的样子。

### 这一轮的账

| | 之前 | 之后 |
|---|---|---|
| 「抖动」用例 | 6 | 实为 3，各自是一个确定性 bug |
| 校验侧 bug | 0（误报轴 0/60） | **3**（空主体集合、`\b` 边界、撤回段落） |
| 描述改动 | — | 1 条（r09），有效 |
| 模型侧问题 | — | 1 条（d06 把持仓数字写进能力说明），不动 |

方向 B 的结论：**在温度 0 下，抖动几乎不是模型的随机性，是确定性 bug 被输入的
微小差异调制出来的**。分类器把 6 条抖动变成了 3 个可复现的 bug，每个都有一条
用真实 fixture 写的回归测试。

### 全量重跑（89 × 3 × 四档）

m07 单独复测 10/10。校验器改了三处，headline 表重记：

| | routed | production | agent |
|---|---|---|---|
| 通过率 | 95% → **96%** | 93% → **95%** | 96% → 96% |
| 每通过 token | 5,517 → **5,216** | 4,226 → **4,137** | 10,127 → **9,266** |
| 重写丢事实 | 1 / 267 | **0 / 267** | 1 / 267 |

production 涨的 2pp 和三档都降的成本来自同一处：被误判的初稿不再触发重写。
新轴「重写丢事实」在全量上第一次有了读数，三档共 2 次，都是 p04（当日盈亏 +
组合风险）：初稿多写了一个算不出来处的百分比，重写把它删掉的同时把当日盈亏也
删了。

修它花了两次，第一次是错的：

| p04 × 10（routed） | 打回 | 其中丢事实 |
|---|---|---|
| 只说哪些数字错了（原版） | 3 | 1 |
| 加「这些数字是对的，只改列出的、别动其余」 | 3 | 1 |
| 再加「你的回复会**整体替换**初稿，请把完整答案重发」 | 3 | **0** |

第二行看初稿和重写原文才明白：模型把「只改列出的」理解成「只回被改的那句」，
那一句就成了整个答案。它没法知道初稿不会被保留——在它看来这是一段对话，上一条
还在。第三行补的是这个事实。同一个规律的又一次：**补一个模型发现不了的事实有效，
下一条指令无效**。随后的全量重跑：三档共 49 次打回，**重写丢事实 0 次**（上一次
全量 2 次）。新增 `partial_rewrite` 标记（重写丢了初稿过半的溯源数字），把「只回
了一段」和「整段改坏」分开计。

这次全量还抓到一个新的归属误报：c07 的表头「资金流 CMF(20)」，20 被记到了前面
的 SMH 名下。指标的回看参数和 「52 周」 里的 52 是一类东西，遮掉，测试钉住。

定义上的一个修正：第一次全量里 agent 档还有两条（c02、v01）初稿事实齐全、重写后
仍然溯源失败——同样的编造数字写了两遍。那不是重写把答案改坏，是校验对了、模型
没照办，所以「重写丢事实」只算最终答案**丢了初稿有的事实**的情况。

production 和 routed 的 1pp 差不再全在 `ranking`（97 → 90），`dead_end` 也掉了
（95 → 81）；`recovery` 反而更好（73 → 80）。8 次上限对开放式问题的影响比上一轮
看到的分散。

## 留出集：15 条没调过的问题

开发集的 98% 路由准确率和 95% 通过率有一个共同的弱点：路由的信号表是对着这 89 条
写的，检查是对着它们的失败修的。要知道下一条用户真打的问题会怎样，得用没见过的。

来源是 Telegram 实测时真实发过的问题（A–F 组和用户自己打的），标注时不看
`router.py`，逐字重复开发集的 7 条被一条测试剔掉，写操作和多轮省略因评测不覆盖
排除，剩 15 条。跑一次，不改代码：

| | baseline | routed | **production** | agent |
|---|---|---|---|---|
| 通过率 | 47% | 84% | **82%** | **100%** |
| 路由准确率 | — | 87% | 87% | — |
| 每通过 token | — | 6,101 | **4,216** | 10,693 |
| 归属误报 / 重写丢事实 | — | 0 / 0 | 0 / 0 | 0 / 0 |

对照开发集（routed 96%、production 92–95%、路由 98%），掉了 10pp 左右，而且**掉的
地方非常集中**：

- **路由漏了两条，各 3 次，占 routed 全部失败的 6/7。** x10「木头姐最近在买什么，和我
  持仓有重叠吗」、x11「CPI 和 NFP 最近怎么样，对我持仓有什么影响」都被留在快路径，
  一张卡答不了两个主题。两条形状一样：多主题信号靠主题词表，词表里没有「木头姐」
  和「NFP」。这两条在建留出集时的路由干跑里就看到了，**没改**——改了它就不是
  留出集。
- **剩下的失败是老形状**：x04、x07 把内部人三笔卖出加成 $21.69M 而没写算式，溯源
  按设计拒绝。开发集里 c02、r08 是同一件事。
- **完整循环 45/45。** 绕过路由，模型驱动的部分在没见过的问题上没有掉分。

结论写在第六条：过拟合的是手写规则，不是模型循环。修法明确（词表加两个词），
但加了就要再造一份留出集来验证，这一份已经用掉了。两条错误标签：0。

## 第二个模型：gpt-4.1-mini

六条结论都是在 deepseek-chat 上得出的。换一个模型跑同一套评测，看的是这些结论
是关于机制的还是关于某个模型的。

### 第一次：被限流污染

第一次全量（89 × 3 × 四档，另加留出集）**不能当分数用**：账户是 200k TPM，四个并发把窗口打满，HTTP 429 在 267 次 agent 运行里
砸出 27 条抖动，全部被分叉分类器标成 `error`——这一类存在的意义就是这一天。

数字本身作废，但有三样东西不依赖那次运行干净不干净：

- **路由准确率 98% / 87% 一字不差。** 路由是规则，与模型无关；留出集上漏的还是
  x10、x11 两条。
- **归属检查漏了一类主体提法。** m06「AMD（-0.09）和TSLA（-0.21）」被标成 AMD←-0.21，
  x10「COIN（7.20%）和ROKU（4.10%）」被标成 COIN←4.10。`\b` 在「和」与「TSLA」
  之间不成立，紧贴中文的 ticker 没被识别为主体，数字就落到了前一个被看到的名字上。
  deepseek-chat 习惯写「和 TSLA」带空格，十五轮没撞到；gpt-4.1-mini 不写空格，
  第一次就撞出三个。修法和第 14 轮 13F 那次相同：边界改为「非字母数字」。
  **换模型的第一个收获是校验器的 bug，不是模型的分数。**
- **工具选择有模型风格。** 「我持仓里哪只离财报最近」deepseek-chat 调一次
  `earnings_calendar`；gpt-4.1-mini 三次都是 `portfolio_view` 加 8 次 `earnings_view`，
  答案对、超预算、漏了标注要求的那张卡。它整体更省：每例 2.0 次调用、2,434 token，
  对 deepseek 的 3.4 次、5,210 token；超预算 0%。这两点在干净的重跑里再确认。

客户端对 429 的退避从 1 s、2 s 改为 2、4、8、16、30、30 s，让每分钟窗口真的滚过去；
重跑用 `EVAL_WORKERS=2`。

### 第二次：干净的数字

`error` 类归零。两个模型，同一套代码、同一批问题、同样的 89 × 3 和 15 × 3：

| | deepseek-chat | | gpt-4.1-mini | |
|---|---|---|---|---|
| | 通过率 | 每通过 token | 通过率 | 每通过 token |
| routed（开发集） | 96% | 5,455 | **84%** | **3,098** |
| production（开发集） | 92–95% | 4,404 | 81% | 3,018 |
| agent（开发集） | 97% | 9,396 | 78% | 6,518 |
| routed（留出集） | 84% | 6,101 | 71% | 4,140 |
| agent（留出集） | 100% | 10,693 | 76% | 8,172 |
| 路由准确率 开发 / 留出 | 98% / 87% | | 98% / 87% | |
| 归属误报 · 重写丢事实 | 0 · 0 | | 0 · 0 | |

哪些是机制的，哪些是模型的，现在能分开说了：

- **机制层面的读数完全一致。** 路由准确率一字不差（它是规则）；归属误报 0/267 × 3，
  重写丢事实 0/267 × 3，两个模型都是。校验器修好之后不挑模型。
- **通过率差 12–19pp，token 少 40%。** gpt-4.1-mini 每例 2.0 次调用对 deepseek 的 3.4，
  超预算 0–1% 对 11–16%。它更省，也更早停：多数失败是「工具漏调」——问「哪只离财报
  最近」它调 8 次 `earnings_view` 自己比，不调那张日历卡；问「CRWD 什么时候财报，8-K
  有什么」它两张卡都调了，答案里却没有日期。后一种要看答案原文，可能是答案键只认
  ISO 日期格式而它写「9 月 6 日」——这会是评测的偏差，不是模型的。存了每个答案的 JSON
  可以用 `python -m v2.agent.eval.rescore` 换答案键重打分，不用再花一次钱。
- **在 gpt-4.1-mini 上，完整循环反而不如路由**（78% 对 84%，留出集 76% 对 71% 又反过来）。
  deepseek 上完整循环稳定高 1pp。「路由拿走循环几乎全部上行」这条在两个模型上都成立，
  「完整循环更好」不成立——它是 deepseek 的性质。
- **第 4 条结论有了第二个样本。** 工具选择是模型风格：同一段描述，一个模型读出
  「用日历卡」，另一个读出「逐只查」。描述能影响选哪个工具，但影响的方向随模型变。

结论：六条里关于校验器和路由的（1、3、5、6）跨模型成立；关于「循环比路由好多少」的
数字是 deepseek-chat 的。README 开头的表继续用 deepseek 的数字，因为线上跑的是它。

## 已知限制

- **路由有两条偏差**（m11 / m12），其中 m11 会给出**误导性**的答案，不只是不完整的。
  财报日历卡覆盖 14 天、且会标注关注列表成员，这两件事从 query 的措辞里都看不出来。
  实盘上「我持仓里的半导体股票下次财报都是什么时候？」走快路径，得到的是
  「无 watchlist 或持仓 标的发财报」——而实际日历是 MU 09-30、LRCX 10-21、
  INTC 10-22、QCOM 10-29、ARM 11-04、NVDA 11-17、MRVL 12-01，全部在 14 天之外。
  用户会据此以为近期没有财报，而 MU 26 天后就要发。

  一个尚未验证的假设：m11 和 m12 的区别也许**不是**先验不可判定的。「有没有快发
  财报的」是判定问题，空卡片就是它的正确答案；「都是什么时候」是枚举问题，空卡片
  回答不了它。若这个区分成立，按问句形状（判定 vs 枚举）就能分开这两条。做之前
  需要跑一轮评测确认它不会把一批本该走快路径的查询误升级 —— 主题词表是这个
  路由器里最容易过拟合的地方。两条偏差目前仍用测试钉住，新增偏差会失败。
- **归属检查的成本**：它触发额外重写轮，token 较不开启时高约 30%。
  `AgentConfig.attribution_check=False` 可关闭。误报率已降到 0.75%（routed 为 0），
  但这是**对着 89 条评测集调出来的**，同样是开发集分数。
- **98% 的路由准确率是开发集分数**：规则是对着这 89 条调出来的，真实泛化能力需要
  没见过的 query。
  **留出集跑过一次**（上一节）：routed 84%、production 82%、agent 100%、路由 87%。
  这份留出集已经用掉；下一次改路由要先再造一份。
- **fixture 是手写合成数据**，形状与真实 responder 一致，但不是真实录制。
- **评测没有测到工具自身的成本**，而这个缺口比看上去大：录制观测是瞬时且免费的，
  但线上 `explain_move` 内部会调 `v2.monitoring.attribute`，**每次调用**要花一次
  Tavily 搜索加 Generator / Verifier 两次 LLM。扇出 5 个标的就是 5 次搜索、
  10 次模型调用 —— 这些完全不出现在循环自己的 token 统计里。
  因此生产预算（`bot_bridge.production_config()`）比评测默认值更紧：
  5 步 / 8 次工具 / 90 秒，可用 `V2_AGENT_MAX_STEPS` · `V2_AGENT_MAX_TOOL_CALLS` ·
  `V2_AGENT_MAX_SECONDS` 免部署调整。
- **超预算率 21%（agent）/ 9%（routed）/ 7%（production）**，且**三次证实描述改动
  碰不到它**（程序性提示、价目表、单工具上限各一轮）。剩下的支出结构上是周全
  （对 8 只持仓各扫 2–3 个工具），不是失控 —— 详见上一节。生产的 8 次上限已经把它
  压到 7%，代价是 `ranking` 一类掉 14pp；要不要用 10–15% 的成本把那一类买回来，
  是产品决定。
- **稳定失败 1 条（r07），抖动 3 条已归因**：第 14 轮把 6 条抖动分成 3 条采样噪声
  和 3 个确定性 bug（详见上一节）。d06、r09 各 10/10；m07 的空主体 bug 已修，
  10 次复测待跑。抖动的诊断工具留在评测里：`--repeat` 下输出「抖动分叉点」
  （error / budget / early_stop / tool_choice / wording）和「重写」两节，JSON 带
  `trace` / `answer` / `draft` / `draft_findings`。跑法：
  `EVAL_MODES=production EVAL_CASES=… EVAL_REPEAT=10 poetry run python v2/agent/run_eval.py`。
- **评测的分辨率约 ±2pp**：同一份代码两次全量 production 95% 与 92%。要分辨比这更
  小的差别，得把 `--repeat` 提到 10，成本三倍多。写进 headline 的数字都是单次全量，
  读的时候要带这个误差。
- **production 的稳定失败 4 条**（m11 路由偏差、r01 漏调 earnings_view、r07 提前收尾、
  v01 8-K 超时后编造数字）。r01 和 r07 都是「够了」信号缺失的形状，描述改不了。
- **production 的 8 次上限是软的**：检查在每步开始时做，一步扇出 3 个调用会整步
  执行，m07 的通过运行稳定是 10 次而不是 8 次。改成硬上限会截断合法的逐仓扫描，
  没改，先记下。

## 1. 差别在哪：控制流归谁

```python
# 现状 —— v2/bot/commands.py:669 cmd_nl，24 分支 if/elif
intent = classify(text)            # LLM 选一个 label
answer = DISPATCH[intent](args)    # 代码选函数，调用恰好一次，结束

# 本包 —— v2/agent/loop.py:run_agent
while not done:
    response = llm(messages, tools)          # 模型看着完整历史决定下一步
    if not response.tool_calls: break
    results  = execute(response.tool_calls)  # 并行执行
    messages += observations(results)        # 结果回灌，影响下一步
```

**LLM 在循环外 vs LLM 在循环里。** 其余全部差异都是这一条的推论：

| | 单跳路由（现状） | Agent 循环（本包） |
|---|---|---|
| 执行路径 | 编译期确定，共 24 条 | 运行时长出来，步数不定 |
| 反馈闭环 | 无——分类器看不到工具返回 | 有——每个观测都进入下一次决策 |
| 工具失败 | 异常冒泡到 `main._error_handler`，用户看到异常类名 | 变成 observation，模型换路线继续 |
| 并行 | 不存在（一次一个） | 一轮内扇出，`ThreadPoolExecutor` |
| 谁写答案 | 没人——原样返回工具卡片 | 模型写，但受 grounding 检查约束 |
| 能回答的问题 | 24 个 responder 的**并集** | 这些工具的**组合空间** |
| 怎么验证 | `assert output == expected`（确定性） | 轨迹指标 + 分布（非确定性） |

### 一个具体例子：「我持仓里哪只最危险」

**基线**：`classify → risk_view → 返回组合级风险卡`。这张卡有集中度和行业暴露，
但没有财报日期、没有内部人交易——**它无法按"综合风险"给个股排序**，因为需要的
事实分散在别的工具里。

**Agent**（`--demo` 的真实轨迹）：

```
步骤 1  portfolio_view()                             ← 先知道持有什么
步骤 2  并行 7 个：risk_view / earnings_view×2 /      ← 用步骤 1 的结果决定查谁
        insider_view / eight_k_view×2 / explain_move
        └ eight_k_view(SMCI) 超时失败 ✗
步骤 3  explain_move(SMCI)                           ← 绕过失败的工具补数据
步骤 4  初稿含「隐含波动率 78.4%」→ grounding 拦截      ← 该数字无任何工具来源
步骤 5  重写，去掉无来源数字 → 16/16 数字可溯源
```

结论「CRWD 最危险」不存在于任何单个 responder 中，是组合出来的。

## 2. 五个机制，各自对应一种真实故障

无边界的 `while` + 会犯错的模型 = 不可用。`loop.py` 里的每个机制都对应一个这个
循环实际会产生的故障：

| 机制 | 位置 | 防的是什么 |
|---|---|---|
| 预算（步数/工具数/墙钟）+ 强制收尾轮 | `loop.py` | 跑飞、以及"超时后什么都没有" |
| 错误即观测 | `registry.py:ToolRegistry.call` | 单个数据源抖动毁掉整轮 |
| 重复调用抑制 | `loop.py:_execute_calls` | tool-calling 循环最典型的死循环 |
| 近因加权上下文压缩 | `context.py` | 这些工具返回的是人读的卡片（`risk_view` >2KB），4 轮就撑爆窗口 |
| 数字溯源检查 + 一次重写 | `grounding.py` | 让模型写字之后重新拿回原来的防幻觉保证 |

### 关于 grounding：原来的招牌没有丢

`intent.py` 的原始设计信条是 *"The LLM never decides what to say, only which tool
to call"*。允许模型撰写答案就放弃了这条，所以必须换成一条**可机械执行**的规则：

> 答案里出现的每一个数字，都必须能在本轮某个工具返回里找到。

无需第二个 LLM、无额外成本。它抓不到"用正确数字讲错故事"，也不声称能抓——它抓的
是**凭空捏造的数字**，这是研报形态输出里唯一致命的失败模式。序数、计数、年份豁免，
模型自己算出来的数要求说明输入。检查不通过 → 带着未溯源清单退回重写一次。

对比时必须诚实的一点：**基线的溯源率恒为 100%**，因为它压根不写字。这是它真实的
优势，代价是它只能回答单工具能回答的问题。CLI 的对比表里明写了这句。

## 3. 权限边界

24 个工具里有 4 个会写 `state.db`（watchlist 增删、alert 增删）。能自主写入的
循环和只读的循环是两个风险等级，所以写操作**默认关闭**，需要 `--allow-mutations`
显式打开；被拦时模型收到的是一条可读的 observation（"说明你本来要改什么，不要重试"），
而不是静默失败。

## 4. 为什么工具层是惰性的、为什么不用 LangChain

- `registry.py` 里存的是**点分路径字符串**而不是函数对象，工具真的被调用时才
  `importlib` 解析。所以本包在裸沙箱（没有 numpy / telegram / langchain）里也能
  导入和测试，同时 bot 的启动开销不变。
- LLM 客户端是 stdlib `urllib` 直接对 OpenAI 兼容的 `/chat/completions` 协议，
  没有引入新依赖。Agent 循环的工程难点正是消息列表、tool_call 载荷和 token 记账，
  这三样不应该藏在框架后面。副作用是 provider 可移植：改 `AGENT_LLM_BASE_URL`
  即可切 DeepSeek / Groq / Gemini / 本地 Ollama。

```bash
AGENT_LLM_BASE_URL=https://api.deepseek.com/v1   AGENT_LLM_MODEL=deepseek-chat
AGENT_LLM_BASE_URL=https://api.groq.com/openai/v1 AGENT_LLM_MODEL=llama-3.3-70b-versatile
AGENT_LLM_BASE_URL=http://localhost:11434/v1      AGENT_LLM_MODEL=qwen3   # 零成本
```

## 5. 测试策略：为什么不能沿用现有那套

现有项目有 490 个 sandbox 测试，能断言"格式化卡片字节相等"——**这件事做得到，
恰恰因为它不是 agent**。同一个输入两次可能走不同路径、调不同工具、步数都不同，
`assert output == expected` 直接失效。

所以这里测的是**控制流**，模型被脚本化（`ScriptedLLM`），把"工具失败能不能恢复"
从轶事变成断言：

```
test_multi_step_run_uses_earlier_results_to_choose_later_calls
test_failed_tool_does_not_end_the_run
test_repeated_identical_call_is_suppressed
test_budget_exhaustion_still_produces_an_answer
test_ungrounded_answer_triggers_one_repair_round / test_repair_happens_at_most_once
test_old_observations_are_compressed_but_recent_ones_are_not
test_baseline_cannot_answer_a_multi_hop_question
```

`fixtures.py` 提供录制观测，让评测确定性可复现——**工具走网络的 agent 根本无法做
回归测试**。这也顺带解决了"别人 clone 下来没有付费数据源 key"的问题。

## 6. 基线的分类器：优先用生产那份，缺依赖时用同源移植

`v2/bot/intent.py` 依赖 LangChain。如果运行环境只装了一个 LLM key（比如新建的
conda env），基线那半边会 `ModuleNotFoundError`，对比只剩一半。

所以 `baseline.resolve_classifier()` 优先 import 生产分类器；import 失败时退回
`intent_port.py`——它**不复制 prompt**，而是用 `ast.literal_eval` 从
`v2/bot/intent.py` 源码里把 `_SYSTEM_PROMPT` 和三个白名单读出来。因此 bot 改了
prompt，基线跟着改；常量被重命名则显式报错，而不是默默测一份过期副本。CLI 会打印
本次用的是哪一个。

## 7. 路由层：什么时候才值得花 10 倍成本

实测（CLI 对比表）：单跳 1 次 LLM 调用 / ~1.2s；agent 4–5 次 / ~11s / ~14k token。
**10 倍成本只在单跳答不了的问题上才划算**，所以需要一个路由层决定走哪条。

`router.py` 的硬约束：**路由本身不调 LLM**。用「分类器已经产出的 intent」+ 正则，
边际成本为零——否则为了省钱先花一次钱，逻辑不成立。

三种 mode 就是灰度顺序：

```bash
V2_AGENT_ROUTING=off           # 默认。全走现状，合并代码不改变任何线上行为
V2_AGENT_ROUTING=unknown_only  # 只接分类器的死胡同（现在回「❓ 没听懂」那些）
V2_AGENT_ROUTING=heuristic     # 全部信号
```

信号表（命中即进 agent，按置信度排序，先命中者胜）：

| 信号 | 判据 | 例子 |
|---|---|---|
| `superlative` | 最(排除最近/最新/最后) · 哪只 · 对比 · 谁更 | 我持仓里哪只最危险 |
| `collection` | 持仓里/关注的/watchlist + 无单一 ticker | 我持仓里有哪些快发财报了 |
| `multi_ticker` | ≥2 个非缩写的大写代码 | NVDA 和 AMD 对比一下 |
| `causal_portfolio` | 为什么 + 盈亏/组合词 + 无 ticker | 我这周为什么亏钱 |
| `compound` | 并且/还有/另外 或 ≥2 个问号 | AAPL 财报怎么样，另外内部人在卖吗 |
| `unknown_intent` | 分类器归类失败 | 今天有什么值得注意的 |
| `explicit_ask` | `/ask <问题>` | 用户强制，任何 mode 下生效 |

两个容易写错、已用测试钉死的细节：

- **`最近`/`最新`/`最后` 不是比较级**。「AMD 最近有什么 8-K」必须走快路径。
- **枚举类 intent 豁免**。「我关注了哪些股票」提到集合，但 `watchlist_view`
  一跳就返回整个集合；除非同时要求排序（「watchlist 里哪只最值得关注」），
  那时比较级信号优先。

## 9. 接到 bot：两行

**已接入**（`v2/bot/commands.py:cmd_nl`，+32 行）。`bot_bridge.telegram_hook` 是
bot 唯一需要知道的接口：

```python
agent_parsed = None
if agent_bridge is not None and agent_bridge.enabled():
    handled, agent_parsed, text = await agent_bridge.telegram_hook(
        text, update.effective_chat.id, placeholder)
    if handled:
        return

parsed = agent_parsed or await _run_blocking(intent.classify, text)   # 原有一行
```

**接入点在 if/elif 分发链之前，不是在它的 `else: # unknown` 分支里。** 我最初的
方案写在那个分支，是错的：那里只有分类器放弃时才到得了，而路由的比较 / 集合 /
多主题信号所针对的问题**都会归类到某个 intent**、在更早的分支被分发掉，
因此永远走不到 else。

四个细节：

- `enabled()` 默认 `False` —— **合上这段代码不改变任何线上行为**，靠环境变量灰度。
- hook 把 `parsed` 交还给调用方，**被路由的问题不会被分类两次**。
- 指代消解发生在分类**之前**，所以补全后的问题可能由快路径答掉；无论谁答，
  这一轮都会被记入会话，下一轮才能解析「它」。
- import 与调用都包了 `try/except`：agent 层出任何问题都不能让 bot 起不来或
  让一条消息没有回复，失败一律退回原有路径。

两个设计细节：
- `parsed` 由调用方传入。bot 走到这个分支时已经付过一次分类的钱，桥接层再分类一次
  就是每条消息双倍成本。
- 进度回调用 `make_threadsafe_progress()` 跨线程边界（`run_agent` 是同步的、跑在
  executor 线程，`edit_text` 是 bot 事件循环的协程），fire-and-forget：
  掉一条进度绝不能把答案带下去。

## 11. B2：10-Q MD&A 措辞解读（`mda_reader.py`）

`v2/sec/ten_q_parser.py` 已经回答了**变了什么**：哪些 MD&A 段落相对上季是新增的、
新增了几条风险因素、有没有 going concern / 重大缺陷。这些是 diff 和正则的确定性事实，
自己就能升 P0，**这一层不能改动也不能抑制它们中的任何一条**。

管线答不了的是**这个变化意味着什么**。一段关于「客户验收周期拉长」的新增措辞，
读者要么认得要么划过去。这个判断是开放的，所以模型该在这儿——而且只做加法。

### 为什么这一层没有工具

本包前面几块是工具循环，因为它们的问题只能靠取数回答。这个问题不用：文本已经在
手里了，业绩数字也随卡片一起进来。为了「让 B2 看起来也像 agent」而接几个工具，
只会增加延迟、token 和失败面，换不到任何东西。**它就是一次受约束的调用**，
工程含量在输出之后发生的事情上。

### 校验比本包其他任何地方都严

别处的判据是「数字能溯源」。这里模型读的是散文，风险不在数字而在**转述**——
把一段披露悄悄说得比原文更好或更坏，才是财报推送里真正致命的失败。

所以每条解读必须附一段**逐字引用**，按空白归一化后做子串匹配，且
**只对照模型实际看到的那份语料**（段落发送前会截断，校验就对着截断后的文本做）——
否则引用可能"验证通过"于模型从未见过、只能靠猜的正文。引用找不到就丢弃，
不重写不软化。方向是闭合枚举，解读里的数字照样过数值溯源。

### 四个正交判据

一个 pass/fail 对改进几乎没用：工具调错和事实丢失长得一模一样，但要反着修。
所以每条按四个轴独立打分，`passed` 是它们的合取：

| 判据 | 说明 |
|---|---|
| 工具召回 | 需要的工具调到了吗。**多调不扣分**——多调是成本问题，计入成本指标 |
| 事实召回 | 该出现的事实活到回复里了吗。每个事实是一组可接受表述（`2026-09-06` / `9月6日` 都算） |
| 纪律 | 有没有调不该调的工具、有没有输出禁止内容（典型：这只没数据，就把另一只的数字搬过来） |
| 溯源 | 数字能否追到观测。**编数字的答案不是正确答案**，所以它在 `passed` 里而不是脚注里 |

### 消融

```
baseline           单跳（要打败的对象）
agent              完整循环
routed             路由逐条决定（生产形态）
agent_no_parallel  关并行 → 分离延迟收益
agent_no_repair    关溯源重写 → 分离该机制的价值
agent_tight        3 步 / 4 次工具 → 预算到底重不重要
```

`routed` 是最值得看的一行：它应该在通过率上贴近 `agent`，成本上贴近 `baseline`。
**如果没有，就说明路由的信号表是错的。**

### 溯源检查的三个假阳性（实测发现并已修）

3 次采样的全量运行显示，agent 55 个被拒数字里 **42% 是四舍五入**，另有若干是单位
换算和 SEC 条款号 —— 也就是说这个检查当时**主要在拒绝正确答案**。逐条核对后确认
是检查的缺陷，不是模型的问题：

| 被拒数字 | 观测里的原文 | 性质 |
|---|---|---|
| `15,852` | `$15,851.57` | 四舍五入 |
| `578` | `$57.80B`（模型写「578 亿」） | 单位换算 |
| `919` | `$9.19M`（模型写「919 万」） | 单位换算 |
| `5.02 / 2.02 / 1.01` | 8-K 的 Item 条款号 | 根本不是数量 |

现在一个数字有四条溯源路径：原样出现、**位数相同的等价量**（`57.80B` ↔ `578 亿`
按有效数字比对）、**在观测值 0.5% 以内**（四舍五入）、以及 `Item` 后的标识符豁免。

**这不是放宽标准**：没写算式的加总（`22.4+18.2+14.1=54.7` 只写 `54.7`）仍然一律拒绝。
那一条改在 prompt 里 —— 要求把算式写出来，而不是让检查去猜。

### 溯源失败要能拆开看

首轮全量运行里，agent 的 17 条失败有 14 条是「数字无法溯源」。这个统计本身不可行动：
**模型编了一个数**和**模型把观测里两个数加起来但没写算式**在这个指标里长得一模一样，
而它们要反着修（前者收紧 prompt，后者考虑放宽校验）。

所以 `grounding.diagnose()` 把每个被拒的数字分类：`rounding`（观测里有近似值）、
`sum` / `difference`（存在算术解释）、`unknown`（找不到任何来源）。

比率（a/b×100）试过但**删掉了**：观测里数字一多，几乎任何目标都能被某个比率巧合命中，
那会把编造的统计洗白成「合法运算」，正好背离这个诊断的目的。同理，`sum` 只说明
「存在一个算术解释」，不等于模型真做了该运算 —— **只有 `unknown` 可以放心当作编造处理**。

### 归属检查：数字是真的，主体是错的（`attribution.py`）

溯源检查问的是「这个数字在观测里有没有」。三轮评测下来它抓编造抓得不错，但对它下面
那一层是全盲的，而那一层在金融产品里更致命：

```
用户问 ARKQ 的持仓 → 工具只有 ARKK → 模型报出 "TSLA 9.80%"
用户问每只持仓的机构比例 → 只有 NVDA 有 → 模型给每只都套上 "Vanguard 8.94%"
```

**每个数字都是真的、都能溯源，错的是主体。** 两轮 prompt 加固完全没动它
（h04 / h07 稳定 0/3）—— 这与前面「模型不写算式」是同一个现象：**校验器不强制的规则，
模型不会遵守**。所以它必须变成一个检查。

机制是**所有权**：每条工具返回都是为某个主体取的（参数里的 ticker / symbol / manager），
里面的数字就属于那个主体。答案里一个数字紧跟在另一个主体名字后面、而它属于别人、
且不属于任何"中性"结果时，就是张冠李戴。

两个必须处理的细节，都来自真实误报：

- **嵌套主体**：ARKK 的持仓卡印着 `TSLA 9.80%`，这个权重既属于 ARKK 也属于 TSLA。
  不处理的话，任何正确引用持仓卡的答案都会被判错。
- **窗口边界**：一个数字归属**最近的前一个主体**，窗口必须在下一个主体处截断。
  否则「NVDA 占仓 18.2%，CRWD 占仓 22.4%」会把 CRWD 的权重算到 NVDA 头上。

单靠数字所有权还看不见 h04 那种**框架性错误**（ARKQ 的每个数字其实都正确归属给了
各自的成分股，错的是"这是 ARKQ 的"这句话）。补一条针对性规则：**查过、但返回里
一个数字都没有的主体，不得被写成有数据**；答案里明说了「没有 X 的数据」则豁免。

失败会触发和溯源同一套重写机制；重写后仍不通过，`stop_reason` 为
`final_answer_misattributed`，bot 侧前置警示。可用 `AgentConfig.attribution_check=False`
关掉。

### 一条 case 可以从构造上就不可能通过

`h07`（「我持仓里每只的机构持股比例」）的判据是**禁止出现 `Vanguard 8.94%`** ——
但那正是 NVDA 的真实机构持股。**任何正确回答只要报了 NVDA，就必然包含这个字符串。**
这条 case 连续四轮 0/3，我为它改了两轮 prompt、加了一整个归属检查，**根因却在我的
标注里**。

一般化的规则（已加进守卫测试）：

> 禁止字符串只有在 case 有**特定主体**、且该字符串属于**另一个主体**时才成立。
> 面向整个组合的问题没有这样的主体，它的要求必须表达成**行为断言**
> （「有没有承认缺数据」），而不是禁止字符串。

这和前面「6 条 case 没有任何断言因而必然通过」是同一类 bug 的两个方向：
**一个让所有模式白拿分，一个让所有模式白丢分**，两者都不会报错，都只会安静地
让分数失真。

### 评测集自己也要被测

评测代码是判别别人的代码，它的 bug 比被测代码的 bug 更坏——会产出一个看起来
权威的错数字。所以 `test_eval.py` 里除了打分器和执行器，还机械校验**答案键本身**：

> 每条 case 断言的事实，必须真的能在录制观测里找到。

否则那条 case 从构造上就不可能通过，套件会对所有模式**等量地**低报——这是最难
察觉的一类评测 bug。这条检查在写 case 的过程中就抓出过我自己标注的错误。
